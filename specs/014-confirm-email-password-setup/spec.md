# Feature Specification: Confirm Email → Password Setup Redirect

**Feature Branch**: `014-confirm-email-password-setup`
**Created**: 2026-03-18
**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - New User Sets Password After Confirmation (Priority: P1)

A newly created user clicks the confirmation link in their welcome email. After the system confirms their email address, they are automatically redirected to the password setup page where they can choose a password and gain full access to their account — without any manual navigation steps.

**Why this priority**: This is the entire purpose of the feature. Without it, newly confirmed users are stranded with no clear path to set a password and log in.

**Independent Test**: Can be fully tested by simulating a successful email confirmation and verifying the user is redirected to the password setup page with a valid token pre-filled.

**Acceptance Scenarios**:

1. **Given** a new user with a valid confirmation token, **When** they visit the confirmation page and the confirmation succeeds, **Then** they are immediately redirected to the password setup page
2. **Given** the redirect to the password setup page, **When** the user arrives, **Then** a valid password setup token is embedded in the URL so the page loads ready for input
3. **Given** the user is on the password setup page with a valid token, **When** they enter and confirm a new password and submit, **Then** their password is set and they are redirected to sign in

---

### User Story 2 - Confirmation Failure Still Shows Error (Priority: P2)

A user with an invalid or expired confirmation token visits the confirmation page. The error behaviour from the previous iteration remains unchanged — no redirect occurs, and the error state is shown as before.

**Why this priority**: The error path must not be broken by the new success behaviour. Regression protection is essential.

**Independent Test**: Can be fully tested by simulating a failed email confirmation and verifying the error panel is shown with no redirect.

**Acceptance Scenarios**:

1. **Given** a user with an invalid confirmation token, **When** they visit the confirmation page, **Then** the error panel is shown with an explanatory message and recovery links — no redirect occurs
2. **Given** a user with no token in the URL, **When** they visit the confirmation page, **Then** the error panel is shown immediately — no redirect and no network request

---

### Edge Cases

- What happens if the confirmation succeeds but the system cannot generate a password setup token? (The confirmation result is treated as a partial failure; the user sees the error panel with a message to contact support rather than being redirected with an invalid or missing token)
- What happens if the user has already set a password and clicks the confirmation link again? (The confirmation endpoint returns an error; the error panel is shown as in US2)
- What happens if the password setup token embedded in the redirect URL expires before the user submits their new password? (The reset-complete page — unchanged — already handles expired tokens with its own error state)

## Requirements *(mandatory)*

### Functional Requirements

**Confirmation Endpoint**

- **FR-001**: After successfully confirming a user's email, the confirmation endpoint MUST generate a password setup token for that user using the same mechanism as the existing password reset flow
- **FR-002**: The confirmation endpoint MUST include the password setup token in its success response alongside the existing confirmation message
- **FR-003**: The password setup token included in the response MUST be valid for use by the existing password setup page — no separate token type is introduced

**Confirmation Page**

- **FR-004**: On receiving a successful confirmation response, the confirmation page MUST redirect the user to the password setup page with the password setup token present in the URL
- **FR-005**: The redirect MUST happen automatically — no additional user action is required between email confirmation and arriving at the password setup page
- **FR-006**: If the confirmation response does not include a password setup token (e.g., due to a server-side failure), the confirmation page MUST show an error state rather than redirecting with a missing or empty token
- **FR-007**: The confirmation page's error states (invalid token, missing token) MUST remain unchanged

**Unchanged Components**

- **FR-008**: The password setup page MUST NOT be modified — it already handles the full password setup flow
- **FR-009**: No new pages, UI components, or token types are introduced by this feature

### Key Entities

- **Password Setup Token**: A single-use token generated by the confirmation endpoint after a successful confirmation, valid for use by the existing password setup flow; shares the same structure and expiry rules as a standard password reset token

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new user can complete the full onboarding sequence — click confirmation link, set a password, sign in — in a single uninterrupted flow with no manual navigation steps
- **SC-002**: The confirmation page's error states (invalid token, missing token, no token) all continue to function exactly as before — zero regression in error behaviour
- **SC-003**: The password setup token delivered via the redirect is valid 100% of the time when the confirmation succeeds — no user reaches the password setup page with a broken or missing token due to this feature
- **SC-004**: No new page, UI component, or token type is introduced — the feature delivers its outcome entirely through changes to existing components

## Assumptions

- The existing password reset token generation mechanism is available to the confirmation endpoint as an internal operation — no new infrastructure is needed
- The password setup token expiry follows the same rules as a standard password reset token (same duration, same single-use invalidation on submission)
- The confirmation page already receives and processes the API response body; it can read the `passwordResetToken` field from the success response without structural changes to the confirmation flow
- The existing password setup page (`reset-complete.html`) reads its token from the URL query string and handles all validation and error states — no changes needed
- If the server returns a 200 but omits the `passwordResetToken` field (e.g., due to a bug), this is treated as a failure and the error panel is shown
