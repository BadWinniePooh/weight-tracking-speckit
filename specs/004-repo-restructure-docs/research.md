## 2. Configuration File Path Analysis

**Decision**: No internal path changes are needed in any moved config file.

**Rationale**: All path references in the config files are relative to their own location or to the Vite `root`. After moving to `frontend/`, each relative reference resolves correctly within the new directory:

| File | Reference | Resolves to (before) | Resolves to (after) | Change needed? |
|------|-----------|----------------------|---------------------|----------------|
| `vite.config.ts` | `root: "src"` | `<root>/src` | `frontend/src` | No |
| `vite.config.ts` | `outDir: "../dist"` | `<root>/dist` | `frontend/dist` | No — inside Docker build context `/app/dist` which is correct |
| `tsconfig.json` | `"src/ts/**/*.ts"` | `<root>/src/ts/` | `frontend/src/ts/` | No |
| `tsconfig.json` | `"tests/**/*.ts"` | `<root>/tests/` | `frontend/tests/` | No |
| `vitest.config.ts` | `"tests/**/*.test.ts"` | `<root>/tests/` | `frontend/tests/` | No |
| `Dockerfile` | `COPY package.json ./` | Build context root | `frontend/` root | No — context changes |
| `Dockerfile` | `COPY public/config.json.template ...` | `<context>/public/` | `frontend/public/` | No — context changes |
| `Dockerfile` | `COPY nginx.conf ...` | `<context>/nginx.conf` | `frontend/nginx.conf` | No — context changes |
| `Dockerfile` | `COPY entrypoint.sh ...` | `<context>/entrypoint.sh` | `frontend/entrypoint.sh` | No — context changes |

**Key insight**: The `Dockerfile` references are all relative to the Docker build context. Changing the build context from `.` (repo root) to `./frontend` in `docker-compose.yml` is the only file that needs editing.

## 3. Docker Compose Change

**Decision**: Change `frontend.build.context` from `.` to `./frontend` in `docker-compose.yml`.

**Rationale**: The only required change to make Docker find the moved Dockerfile and all files it copies.

```yaml
# Before
frontend:
  build:
    context: .
    dockerfile: Dockerfile

# After
frontend:
  build:
    context: ./frontend
    dockerfile: Dockerfile
```

No other service definitions change.

## 4. Environment Variables Inventory

The following environment variables are configurable by self-hosters. Sourced by auditing `docker-compose.yml`.

| Variable | Service | Default | Effect |
|----------|---------|---------|--------|
| `API_URL` | frontend | `http://localhost:8080` | Backend API URL injected into `config.json` at container start via `envsubst` |
| `AllowedOrigin` | backend | `http://localhost:3000` | CORS allowed origin for the backend API |
| `ConnectionStrings__DefaultConnection` | backend | `Host=db;Database=weighttracker;Username=weighttracker;Password=weighttracker` | Full PostgreSQL connection string |
| `POSTGRES_DB` | db | `weighttracker` | PostgreSQL database name |
| `POSTGRES_USER` | db | `weighttracker` | PostgreSQL username |
| `POSTGRES_PASSWORD` | db | `weighttracker` | PostgreSQL password — **change in production** |

**Note for README**: Operators who deploy on a non-localhost domain MUST set `API_URL` to the backend's public URL and `AllowedOrigin` to the frontend's public URL. The default Postgres credentials MUST be changed for any internet-accessible deployment.

## 5. Docker Named Volume and Data Persistence

**Decision**: Document `weighttracker-data` as the named volume backing PostgreSQL.

**Rationale**: All backup, restore, and rollback runbook procedures center on this Docker named volume. The volume persists across container restarts and updates as long as `docker compose down` (without `-v`) is used.

**Critical operator note**: `docker compose down -v` destroys the volume and all data. The runbook MUST prominently warn against this.

---

## 6. Runbook Procedure Research

### Update Without Data Loss
1. `git pull` (or `docker pull` for released images)
2. `docker compose up --build -d` — Docker Compose rebuilds images and restarts containers; the named volume is unaffected

### Backup PostgreSQL Volume
Use `pg_dump` via `docker exec`:
```sh
docker compose exec db pg_dump -U weighttracker weighttracker > backup-$(date +%Y-%m-%d).sql
```

### Restore from Backup
```sh
docker compose exec -T db psql -U weighttracker weighttracker < backup-YYYY-MM-DD.sql
```

### Rollback a Failed Update
1. `git stash` / `git checkout <previous-tag>` (or pull previous image)
2. `docker compose up --build -d`
The named volume is unaffected by image changes, so data is preserved.

### Troubleshooting
- **Container won't start**: `docker compose logs <service>` reveals startup errors
- **Database connection error**: Verify `ConnectionStrings__DefaultConnection` matches `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`; check `db` service is healthy with `docker compose ps`
- **Frontend can't reach backend**: Verify `API_URL` matches the host and port the backend is actually reachable at; check CORS via `AllowedOrigin`

## 7. Minimum Docker Versions

**Decision**: Document Docker Engine 20.10+ and Docker Compose v2.0+ as minimum requirements.

**Rationale**: Docker Compose v2 (`docker compose`) is required for the `compose.yml` / `docker-compose.yml` format v3.9 and for `depends_on` with `condition: service_healthy`. Docker Engine 20.10 is widely available and supports the health-check features used in this project.
